# eval のケースを点検する

`claude plugin eval` の点数が、skill の働きを本当に測っているかを確かめる。ケースを作るのは `claude plugin eval init` の役目で、この skill は作ったあとのケースを見る。
引数があればそれを plugin のディレクトリとし、なければ作業ディレクトリを対象にする。

## 手順

### 1. ケースがあるかを確かめる

ケースは plugin の `evals/` にある。`plugin.json` の `experimental.evals` に別のディレクトリが書いてあれば、そちらを見る。
ケースがなければ点検はできない。ターミナルで `claude plugin eval init` を実行してケースを作るよう伝えて止める。

### 2. 点検スクリプトを実行する

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/audit.py" <plugin のディレクトリ>
```

`case.yaml` に `scaffold_script` があるケースは、`--scaffold` を付けたときだけ「何もしなかった実行」まで点検する。scaffold はユーザーの権限で bash を動かすので、付ける前に、ケースを書いたのがユーザー自身か組織かを確かめる。

スクリプトは、各ケースについて「Claude が tool を 1 回も呼ばず、何も答えず、ワークスペースが scaffold の作ったままの実行」を想定し、費用のかからない grader（regex、tool_used、tool_order、file_exists）で判定する。そこで合格する grader は、作業をした証拠になっていない。llm と baseline の grader は判定できないので、落ちるものとして点数を出す。

結果は 3 段階で出る。

| 段階 | 意味 |
| --- | --- |
| ERROR | eval が正しく測れない。何もしなくても合格するケース、必ず落ちる grader、読み込めないケースなど |
| WARN | 点数がずれるおそれがある。作業をしなくても合格する grader、絶対日付、`arm: both` の付け忘れなど |
| INFO | 判定できなかった grader や、足すとよい grader の種類 |

ERROR があると終了コードは 1 になる。

Bash を使えない環境では、スクリプトの代わりにケースと grader のファイルを読み、手順 4 と「知っておくこと」の各項目に当たるものを探す。手を抜いた出力で合格するかは、テンプレートと grader の正規表現を突き合わせて確かめる。

### 3. 手を抜いた出力でも試す

テンプレートを写してファイルを作る skill では、「写しただけで中身を埋めていない出力」でも合格する grader がよく混ざる。そうした出力をスクラッチパッドに作り、`--overlay` で重ねて点検する。重ねたファイルは Claude が作ったものとして扱われる。

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/audit.py" <plugin のディレクトリ> --scaffold --overlay <手を抜いた出力のディレクトリ> --case '<対象のケース>'
```

`--overlay` は `--case` で選んだすべてのケースに重なる。出力の形がケースごとに違うときは、ケースごとに実行する。手を抜いた出力の例は次のとおり。

- skill のテンプレートを、指示どおりの場所に写しただけのもの
- 見出しだけで本文が TODO のままのファイル
- 依頼文を言い換えて書いただけのファイル

ここで合格する grader は、テンプレートやプロンプトにある語を探していることが多い。コメント行は数えない、TODO が残っていないことも見る、といった条件を足し、手を抜いた出力では落ちるように直す。

### 4. スクリプトでは見られない点を読む

ケースのファイルを読み、次を確かめる。

1. **依頼の種類がそろっているか。** skill の名前を出す依頼、出さない依頼、関係のない文脈が混ざった依頼、skill を呼んではいけない依頼の 4 種類を、それぞれ 1 件以上置く。呼んではいけない依頼は、skill の説明に近い話題で、別の作業をさせるものにする（ハーネスを作る skill なら「CI のワークフローを作って」）。まったく関係のない依頼では、plugin ありとなしのどちらも合格して差が出ない。
2. **依頼文が実際の利用者の書き方か。** 値や前提に矛盾や打ち間違いに見える箇所があると、エージェントは作業を止めて聞き返す。聞き返して終わった実行は、skill の良し悪しと関係なく落ちる。
3. **結果を見る grader と、手順を見る grader の組になっているか。** 結果は regex、file_exists、llm で、手順は tool_used、tool_order で見る。長い生成物は llm ではなく、regex で中身を見る。llm の判定は、読む文が長いほどぶれる。
4. **grader ごとに、どの失敗を見つけるためのものかを言えるか。** 言えない grader は消す。言えるものは、その失敗の出力で本当に落ちるかを、手を抜いた出力（手順 3）で確かめる。
5. **費用。** 実行の回数は「ケース数 × runs（既定 3）× 2」で、2 は plugin ありとなしの両方を走らせるためである。目安として、harness plugin の 8 ケースでは $28.61 かかった。`--max-cost-usd` で上限を決めて実行する。

### 5. 報告して直す

指摘ごとに、何が起きるかと直し方を短く書く。直すのはユーザーが頼んだときだけにする。直したら手順 2 と 3 をもう一度実行し、新しい ERROR と WARN が出ないことを確かめる。

eval を実行し直すときは、まず 1 ケースを 1 回だけ走らせて動くことを確かめ、そのあと全体を既定の回数で走らせる。1 回だけの結果はぶれるので、それで良し悪しを決めない。

```bash
claude plugin eval <plugin のディレクトリ> --case <ケース名> --runs 1 --ablation none
```

リポジトリに単体テストがあるなら、grader の正規表現がテンプレートでは落ち、正しい出力では合格することを確かめるテストを足すよう提案する。grader を書き換えても、テンプレートのままで合格する形に戻らなくなる。

## 知っておくこと

出典は [公式ドキュメント](https://code.claude.com/docs/en/plugin-evals) と、Claude Code 2.1.31x で実際に eval を走らせて確かめたこと（実測）である。

- **Skill の grader は点数から外れる（公式）。** plugin ありとなしの両方を走らせるとき、`tool: Skill` の tool_used と `arm: with-only` の grader は点数に入らず、plugin ありの実行の目印として出るだけになる。skill を呼ばないことを点数にするには `arm: both` を付ける。
- **slash で読み込んだ skill は Skill の呼び出しとして記録されない（実測）。** `/plugin:skill …` で始まる依頼で `tool: Skill` を見ると、skill が動いていても落ちる。skill のファイルを Read したかを tool_used で見るか、結果だけを見る。
- **file_exists は実行中に作られたファイルしか数えない（公式）。** scaffold が作ったファイルや、Claude が編集しただけのファイルは数えない。中身を `target: {source: file, path: …}` の regex で見る。
- **regex は JavaScript の構文（公式）。** `(?i)` は使えないので `flags: i` にする。`target: trace` は JSON の文字列なので、`"` は `\"` として探す。
- **絶対日付は古くなる（実測）。** 過ぎると正解が変わる。10 年先の締め切りを書いたケースでは、エージェントが打ち間違いを疑って聞き返し、3 回中 2 回落ちた。「今日から 12 時間」のように相対で書く。
- **Bash を許すケースは OS の sandbox の中で動く（公式）。** `~/.aws/config` に `credential_process` があるマシンでは、sandbox を作れずに起動を断った（実測）。Bash を外して Read、Write、Edit だけで済むケースにするか、その設定のないマシンで実行する。
- **並列数は 2 程度にする（実測）。** `-j 4` では API の再試行が重なり、タイムアウトするケースが出た。並列の実行は 1 つの rate limit を分け合う。
- **max_turns の既定は 10（公式）。** ファイルを作るケースでは足りず、上限に達すると実行エラーとして点数が下がる。
